## 一、结论速览

| 问题 | 答案 |
|------|------|
| 性格是否符合剧本 | 两种模式都只有 prompt 约束。上传模式有启发式打分，**但严重度是 medium，不阻塞——故意把冷静角色写成尖叫，验证器仍然判"通过"**（实测得分 0.10 vs 正常 0.60，信号很强却不被采用）。更糟的是：**真实剧本输出的 personality 得分恒为 0.60**（未命中词表的中性值），说明 16 个性状词表对实际角色卡基本失效 |
| 角色一致性（说话人是否越界） | 上传模式**有硬拦截**（critical，且已按 `characters_present` 过滤到本场景角色）；实时模式**完全没有检查**，幻觉角色名会直通前端（实测 2 场景 0 违规，但无任何拦截） |
| 主线/世界书是否偏离 | 上传模式能拦住彻底跑题的输出（0.00 < 阈值 0.12），但**正常输出也只有 0.17-0.35**，余量小，导致阈值不敢调高，只能抓"完全跑题"抓不住"轻微偏题/推进不足"；世界书规则（world_rules）在两种模式都**只做 prompt 注入，没有任何校验** |
| 多轮（跨场景）一致性 | 两种模式都**只靠 prompt 里的历史注入**，没有任何跨场景检查。实测到明确漂移：林晓平均句长 45.7→55.8 字、省略号使用率 14%→**50%**（×3.5），无人发现 |
| 两模式标准是否统一 | **不统一**：对话轮数 3-15 vs 10-20、选项 2-4 vs 2-3、情绪枚举 15 值 vs 12 值、有无验证门控 |
| emotion 合法性 | 校验代码 `VALID_EMOTIONS` **定义了但从未被调用**（死代码），两种模式的 emotion 都原样透传前端 |
| 生图实际并发 | **1**（`_img_call_lock` 全局串行锁写死），不是配置里的 4 或 8 |
| 换付费 API 并发 10 能提速多少 | **不改代码则 0 提速**；改 2 处后可达 5-9 倍（实时 6 张：56s → ~6-10s；上传全量 21 张：196s → ~17-28s），但首屏等待基本不变 |

## 二、两种模式的一致性/验证现状对照

| 检查项 | 上传模式（Harness） | 实时模式（realtime_engine） | 说明 |
|--------|---------------------|------------------------------|------|
| 说话人 ∈ 角色卡 | ✅ `character_consistency`（critical，失败重试） | ❌ 无 | 实时只做大小写/别名归一化，查不到就原样输出（realtime_engine.py:1084） |
| 动作旁白 subject ∈ 角色卡 | ⚠️ 净化为普通旁白（dialogue stage） | ❌ 无 | |
| 性格匹配 | ⚠️ 启发式关键词，**medium 不阻塞** | ❌ 无 | 16 个性状词表，角色性格不在表内时默认给满分 |
| 主线符合 | ⚠️ 关键词/bigram，阈值 0.12（终局 0.08） | ❌ 无 | 实时有 `core_conflict/plot_summary` 注入 prompt，但无校验 |
| 世界书规则（world_rules/禁设） | ⚠️ 仅 prompt 注入（`_worldbook`） | ⚠️ 仅 prompt 注入 | 两种模式都没有违规检测 |
| 跨场景情绪/事实延续 | ⚠️ 仅 prompt 注入（`{{choiceHistory}}`、上一轮上下文） | ⚠️ 仅 prompt 注入（上一场景完整旁白+最后 12 条对话） | 无校验、无重复度检测 |
| 对话轮数 | ✅ `dialogue_count`（high，3-15） | ❌ 无（prompt 要求 10-20） | |
| 选项数量/impact 合法性 | ✅ `choice_validity`（high）+ 多样性（medium） | ❌ 无 | 实时默认兜底 1 个"继续探索"选项 |
| emotion 合法值 | ❌ 定义未使用 | ❌ 定义未使用 | 两种模式都原样透传 |
| 连续发言 | ⚠️ medium 不阻塞 | ❌ 无 | 实测索尔维出现 medium 违规并放行 |
| 失败后的动作 | 重试（最多 2 次）→ 三层保底 | 无（直接下发） | |

## 三、验证器检出能力实测（离线坏样本注入，不消耗 API）

构造 5 组输出喂给 `NarrativeValidator`（冷静理性的林晗 + 果断务实的赵远山，节点"危机→到达"）：

| 用例 | 判定 | 未通过的检查 | personality | worldline |
|------|------|--------------|-------------|-----------|
| 正常输出 | ✅ 通过 | — | 0.60 | **0.17** |
| 性格完全相反（冷静者崩溃尖叫、果断者犹豫） | ✅ **通过（漏判）** | consecutive_speaker, personality_match | **0.10** | 0.17 |
| 主线完全偏离（改写成讨论午饭） | ❌ 拦截 | worldline_adherence | 0.60 | **0.00** |
| 幻觉角色（"神秘人"发言） | ❌ 拦截 | character_consistency | 0.60 | 0.17 |
| 无世界线关联但含角色名 | ❌ 拦截 | worldline_adherence | 0.60 | 0.00 |

三个关键结论：
1. **性格检查"检得出、不敢用"**：违背性格的输出打分 0.10，与正常 0.60 拉开 6 倍，但 severity=medium 使其永远不影响结论——这是当前最大的质量漏洞，也是最容易修的一处。
2. **主线检查灵敏度被低阈值锁死**：正常输出只有 0.17，阈值 0.12，余量 0.05。想提高阈值就会大量误杀正常输出，所以它只能抓"完全跑题"，抓不住"轻微偏题/推进不足"。根因是用节点名 2-gram 字面匹配，而非语义判定。
3. **实时模式根本没有这道门**：上传模式验证器发现的问题，在实时模式下无人发现。

## 四、真实输出违规统计（两种模式各实测 1 轮）

实测对象：实时模式《尘封的第四排》（3 角色，场景 1 + 玩家选择后场景 2）；上传模式 回响-DEMO（2 场景，剧本角色 苏然/林晓/杜维明，场景 1-2 的 `characters_present` 只含前两人，✅ 已按场景过滤）。

### 4.1 硬指标：全部干净（0 违规）

| 指标 | 实时 场景1 | 实时 场景2 | Harness 信号 | Harness 碎片 |
|------|-----------|-----------|--------------|-------------|
| 对话条数 | 12 | 12 | 14 | 14 |
| 动作旁白 | 6 | 5 | n/a¹ | n/a¹ |
| 非法 speaker（幻觉角色） | 0 | 0 | 0 | 0 |
| 非法 speaker_id | 0 | — | — | — |
| 非法 emotion | 0 | 0 | 0 | 0 |
| 非法 action subject | 0 | 0 | — | — |
| 最大连续发言 | 1 | 1 | 1 | 2 |
| 选项数 | 3 | 3 | 3 | 2 |
| 旁白字数 | 167 | 204 | 226 | 231 |

说明：角色名/情绪枚举/结构层面的约束，两种模式在实测中都守住了。**问题不在"违规频发"，而在"违规了也没人管"**（第三节已证明性格违背可放行，实时模式连放行机制都没有）。
> ¹ `/api/auto-run` 的同步响应里 `dialogues` 只含 Dialogue 对象，动作旁白在流式 SSE 中以独立 `{"kind":"action"}` 事件下发（dialogue.py:159），不进该列表。所以上表 Harness 的动作旁白数**无法从该路径统计**，不代表"没生成动作旁白"；要量它得走 `/api/session/{id}/generate-stream`。

### 4.2 验证器对真实输出的打分：暴露"词表失效"

| 场景 | personality_match | worldline_adherence | 结论 |
|------|-------------------|---------------------|------|
| Harness 信号 | 0.60 | 0.26 | 0.60 正是"未命中任何性格词表"的中性分 |
| Harness 碎片 | 0.60 | 0.35 | 同上 |

真实剧本输出的 personality 得分恒为 0.60（中性），说明 16 词表对实际角色卡（"克制""内敛""外冷内热"等描述）基本命中不到，**这个检查在真实数据上等同于不存在**——它只能在坏样本注入时给出 0.10 的强信号，却因 medium 不阻塞而不生效。

### 4.3 跨场景风格漂移（新指标，实测有信号）

按角色统计"平均字数 + 省略号率"，跨场景对比：

| 角色 | 模式 | 场景1 | 场景2 | 漂移 |
|------|------|-------|-------|------|
| 林晓 | Harness | 45.7 字 / 省略号 14% | 55.8 字 / 省略号 50% | 句长 +22%，省略号 **×3.5** |
| 苏然 | Harness | 45.9 字 / 29% | 49.2 字 / 17% | 轻微 |
| 周野 | 实时 | 37.5 字 / 25% | 43.2 字 / 40% | 句长 +15%，省略号 ×1.6 |
| 沈砚秋 | 实时 | 25.0 字 / 0% | 25.2 字 / 0% | 无漂移 ✅ |
| 林知夏 | 实时 | 36.2 字 / 0% | 31.0 字 / 0% | 无漂移 ✅ |

结论：**说话风格漂移是真实存在的现象**（林晓一句之内从"少用省略号"变成"一半句子带省略号"），而当前没有任何机制能发现它。5.3 节的"风格指纹"检查可以直接量化并拦住这类漂移，成本为零（纯本地统计）。

### 4.4 动作旁白密度

实时模式 prompt 要求"约每 2-4 句对话穿插 1 条"，实测 12 对话配 6/5 动作（≈ 每 2 句 1 条），处于要求上限。上传模式的 dialogue_v2 模板规则是"整段对话最多穿插 1-2 条"，密度标准与实时模式差 3-6 倍，属于 5.6 需要统一的范围（其真实密度本次无法从 auto-run 响应统计，需走 generate-stream 才能测）。

## 五、统一质量标准方案（建议）

目标：**一套判定规则、两种模式共用、结果可观测、代价可控**。

### 5.1 抽出共享组件 `QualityGate`

把现在只服务 Harness Stage 5 的 `NarrativeValidator` 升级为模式无关的 `QualityGate`，输入统一为"角色集合 + 世界书规则 + 主线节点 + 历史摘要 + 本场景输出"，输出统一为分级结果。Harness 在 Stage 5 同步调用；实时在场景生成完成后异步调用（见 5.4）。

### 5.2 分级与处置（核心设计）

| 级别 | 检查项 | 处置 |
|------|--------|------|
| L1 硬拦截（阻塞，触发重试/修复） | 说话人越界、无对话、选项为空、对话条数低于下限 | 现有能力，保留 |
| L2 自动修复（不阻塞，就地修） | 说话人别名/ID 归一化、非法 emotion 映射到最近合法值、动作旁白 subject 越界降级为纯旁白 | 实时模式已有部分实现，补齐 emotion 映射与越界清理 |
| L3 质量拦截（新提为阻塞） | **性格匹配**（personality_match 由 medium → high）、连续发言（≥3） | 需先校准误报率，建议先在灰度/日志观察一轮再切阻塞 |
| L4 语义判定（LLM-as-judge，采样执行） | 主线推进是否达标、是否违反世界书规则、是否与上一场景事实矛盾、是否重复前情 | 新增，用小模型/低 max_tokens 单次调用，返回结构化标签 |

L4 是解决"关键词匹配天花板"的正路：一次调用同时判 4 项（偏离主线 / 违反设定 / 事实矛盾 / 情节重复），成本约为主生成的 1/10。建议默认对每场景执行，实时模式下可配置为"仅结局场景 + 抽样 30%"以控延迟。

### 5.3 跨场景（多轮）一致性——目前完全缺失的能力

建议加三类可 cheap 计算的检查：
1. **事实账本**：每场景生成后抽取 `{角色状态, 已确立事实, 未解悬念}`（可由 L4 同一次调用附带产出），下一场景生成前作为硬约束注入，生成后校验新场景是否覆盖了"上一场景未解悬念"。
2. **风格漂移指纹**：按角色统计平均句长、省略号率、语气词率（探针已实现），滚动窗口对比，漂移超阈值告警。
3. **重复度**：本场景旁白/对话与前 3 场景做 3-gram Jaccard，>0.35 判"情节重复"。

### 5.4 实时模式的接入方式（不能拖慢体验）

实时是流式演出，不能同步等验证。建议：
- 场景下发照旧（保证不卡）；验证在后台队列执行；
- 判定 L1/L3 失败时：给该场景打 `quality_flag`，SSE 推送一个 `quality_warning` 事件（前端不打断演出，仅日志/调试面板显示），并把失败原因注入**下一次**生成的 prompt（同上传模式的重试反馈机制）；
- 结局场景改为**同步验证**（玩家已进入结算阅读，可承受 2-4s）；
- 与现有分支预生成结合：预生成的场景天然带验证结果，玩家选择时零等待。

### 5.5 阈值与可观测

- 所有阈值进 `config/quillforge_config.yaml` 的 `validationGate.thresholds`（已支持 personality/worldline，需补 emotion 白名单、重复度、漂移阈值、L4 开关与采样率）；
- 两种模式统一输出 `validation` 结构（现有 Harness 有，实时补上），写入场景 YAML，便于回归对比；
- 建议在 `/api/session/{id}/state` 与 `/api/realtime/{id}/state` 暴露 `quality` 摘要，方便自动化测试断言。

### 5.6 标准统一清单（两模式必须一致的部分）

| 项 | 建议统一值 | 现状差异 |
|----|-----------|----------|
| 对话条数 | 8-16（动作旁白不计入） | 3-15 vs 10-20 |
| 选项数 | 3（结局场景与结局数一致） | 2-4 vs 2-3 |
| 旁白字数 | 150-250 | 已一致 |
| emotion 枚举 | 单一来源（validator 或 prompt 之一，另一处引用） | 15 vs 12，且未校验 |
| 动作旁白密度 | 每 3-4 句 1 条，整段上限 3 条 | 每 2-4 句 1 条（实测贴上限）vs 最多 1-2 条 |
| 角色引用 | 一律以 `speaker_id` 为准，name 只做展示 | 实时已用 id，上传用 name |
| 验证门控 | 同一 QualityGate | 实时缺失 |

## 六、生图并发审查（只查看，未改动）

### 6.1 当前生效值（实测核对）

| 层面 | 值 | 位置 | 实际作用 |
|------|----|------|----------|
| **API 调用并发** | **1（硬编码串行）** | `image_gen.py:444` `with _img_call_lock` | 真正的瓶颈，任何配置都改变不了 |
| 队列线程数 | `IMAGE_CONCURRENCY=4`（代码默认 8） | `.env` / `config_manager.py:58` | 只决定多少张图提前排队 |
| 提交间隔 | `IMAGE_STAGGER_SEC=0.5`（默认 1.5） | `image_gen.py:92` | 每张固定 +0.5s |
| 实时素材池 | `max_workers = min(张数, IMAGE_CONCURRENCY)` = 4 | `realtime_engine.py:1404` | 排队上限 4 |
| 立绘抠图 | 1.2-1.5s/张，**串行**（Numba 多线程会崩） | `_rembg_infer_lock` | 与下一张 API 调用重叠，char 多时会成瓶颈 |
| 实时后台池 | 10 线程 | `realtime_engine.py:232` | 够支撑 10 并发 |

**实测吞吐**（同一模型 cogview-3-flash，1344x768 / 768x1344）：
- 今日 3 轮实时（各 4 立绘 + 2 背景 = 6 张）：从第 1 张完成到第 6 张完成 47-53s，**平均 9.3s/张**
- 全量 21 张（1927 索尔维会议剧本，12 立绘 + 9 背景）：首末完成差 196s，**同样 9.3s/张**
- 结论：单张墙钟 ≈ 8.5s（API 8s + stagger 0.5s），立绘额外 rembg 1.3s 基本被重叠吸收

### 6.2 换付费 API、并发开到 10 能提速多少

**先说前提**：只换 key、不改代码 → **提速 0**。因为 `_img_call_lock` 把并发锁死在 1。要兑现 10 并发需要改 2 处（本次未改）：
1. `_img_call_lock` → `threading.Semaphore(IMAGE_API_MAX_INFLIGHT)`
2. `IMAGE_CONCURRENCY` ≥ 10 且 `IMAGE_STAGGER_SEC` → 0

**改完之后的估算**（公式：`T ≈ ceil(N/C) × L_api`，L_api 为付费模型单张延迟，rembg 串行项 1.3s×立绘数 作为下限）：

| 场景 | 张数 N | 现状（C=1，L=8.5s） | L=8s | L=6s | L=4s | 提速 |
|------|--------|---------------------|------|------|------|------|
| 实时一局（4 立绘+2 背景） | 6 | **~56s** | ~9s | ~7s | ~6s | **6-9 倍** |
| 上传模式全量（12 立绘+9 背景） | 21 | **~196s** | ~26s | ~20s | ~17s | **7-12 倍** |
| 小型剧本（4 立绘+5 背景） | 9 | ~84s | ~11s | ~8s | ~7s | 8-12 倍 |

**三个必须说清的边界**：
1. **首屏体验几乎不变**。玩家进游戏只需第 1 张图，现状 ~9s、并发后仍是 ~L_api（单张延迟由模型决定，与并发无关）。提速体现在"全部素材就绪"和后续场景背景陆续到达。
2. **付费模型单张延迟是最大未知数**。若付费档用的是更贵的模型（cogview-4、Seedream 高清档），L 可能反而从 8s 涨到 12-20s，10 并发的收益会被单张变慢吃掉一半甚至更多——**并发数 ≠ 速度，先量 L**。建议换 key 后先跑 1 轮实测（现有探针脚本可直接复用）。
3. **rembg 会成为新瓶颈**。立绘一多（≥12 张），1.3s/张 的串行抠图会压过 API 批次时间；真要提速到 10 倍以上，需要把抠图也并行（多 session 或换 GPU/onnxruntime 多线程），这属于额外改造。
4. 附赠收益：付费档解除串行后可去掉 stagger（省 0.5s/张）、去掉 429 重试（现最长退避 3+6+9=18s）、可关水印（需先与服务商签免责声明）。成本按张计费，需按"每局 6-21 张"估算。

### 6.3 如果只想"小幅提速、不动锁"

现状下唯一安全的免费收益：把 `IMAGE_STAGGER_SEC` 从 0.5 降到 0（免费档会立刻 429，不建议）、或把预生成图片数量减少——都属于配置调整，本次未做，留作后续决策。

## 七、建议执行顺序

1. **P0（1 处改动，收益最大）**：`personality_match` 严重度 medium → high，并给"性格无匹配词表"的角色补 LLM 兜底判定。先跑 5 轮回归看误报率。
2. **P0**：实时模式接入 L1 硬拦截（说话人越界 + 对话条数 + 选项非空），失败原因注入下一次生成 prompt。
3. **P1**：emotion 白名单真正启用（L2 自动映射），消除 `VALID_EMOTIONS` 死代码。
4. **P1**：L4 语义判定（LLM-as-judge）上线，替换 0.12 的关键词阈值；阈值调高到可控误报水平。
5. **P2**：两模式标准统一（对话条数/选项数/角色引用方式），跨场景一致性与重复度检测。
6. **P2（生图）**：确认要换付费 API 后，先测单张 L，再决定是否把串行锁改 Semaphore + 抠图并行。

## 八、实施记录（2026-11-07，已完成 P0 + 内容安全）

### 8.1 P0-1 性格匹配提为阻塞 + LLM 兜底（上传模式）

- `config/quillforge_config.yaml` → `validationGate.thresholds.personalitySeverity: "high"`（默认可一行改回 medium）；
  新增 `personalityJudge: true`、`judgeMaxTokens: 300`。
- 词表命中时仍走启发式打分（零额外调用）；**只有词表零命中**才调用一次 LLM 评审（`prompts/personality_judge.md`，
  在 `NarrativeSUT.judge_personality()` 内渲染与调用，validator 与 core.py 都不含 LLM 逻辑）。
- 实测评审区分度：内向角色喊"都给我闭嘴，这里我说了算"得 0.20，泼辣角色说"我得回去查三天资料"得 0.20，
  正常台词得 0.80；阈值 0.5 ⇒ 前两者 `personality_match` 由 high 拦截并进入重试循环。
- 同一批台词关闭评审时 `personality_match` 为 medium 且 passed=True——正是原报告指出的"词表漏判被静默放过"。

### 8.2 P0-2 实时模式 L1 硬门 + 失败原因反馈

- `RealtimeStorySession._check_scene_quality()`：说话人/`speaker_id`/动作主体越界、对话少于 `DIALOGUE_FLOOR = 8`
  （Prompt 要求 10，留 2 条余量）、旁白少于 10 字。
- L2 先修再判：`_normalize_speakers()`（别名/大小写/`speaker_id` → 标准名）与 `_normalize_emotions()`
  （`EMOTION_ALIASES` 近义词 → `VALID_EMOTIONS`）在 `_postprocess_scene()` 内就地修正，**不占用重试预算**；
  因此"缺少玩家选项"不再进硬门（`_postprocess_scene` 已兜底填 1 条），情绪也不作为拦截条件——它是前端展示标签，
  为它多花一次完整场景生成不划算。`VALID_EMOTIONS` 死代码问题由 L2 映射消除。
- 流式路径（已推送内容不可撤回）只记录 `scene["quality"] = {passed, issues}`；预生成路径
  `_gate_scene_with_retry()` 带原因重试一次，仅当重试结果问题更少才替换。
- 失败原因注入下一场景 Prompt（`_build_scene_prompt(..., quality_feedback=...)`），通过
  `scene["quality"]` + `quality_feedback` 两个通道。
- 3 个真实场景实测：spoken 10 / 12 / 11 条，`quality.passed` 全为 true，`issues` 全为空，**零次重试**；
  情绪标签全部落在标准枚举内。

### 8.3 内容安全（新增，覆盖剧本生成 / 实时生成 / 生图）

三层，全部实现在 `src/content_guard.py`：

| 层 | 位置 | 行为 |
|----|------|------|
| L1 入口拦截 | `routes/realtime.py`、`routes/script_gen.py`、`realtime_engine.initialize`、`script_generator` | `scan_input()` 命中即 HTTP 400 + 中文分类（"您输入的描述包含不支持的内容（色情低俗、毒品制作方法），请调整后重试"），不消耗任何 LLM 调用 |
| L2 生图软化 | `image_gen.py` 两个 prompt builder | `soften_image_prompt()` 只改写视觉描述（裸露/血腥/尸体/自残器具/毒品/武器制法/群体事件），**未命中时逐字返回**，因此 8 位 md5 缓存 key 不变，已有素材零重生成 |
| L3 报错翻译 | `llm_client.py`、`image_gen.py` | 服务商审核类报错（含智谱 `1301`）转 `ContentSafetyError` 中文提示，SSE 以 `event: error` 下发；生图侧跳过无意义的重试直接回退占位图 |

- 词表遵循"高置信、低误伤"：未成年人性内容、色情低俗、自杀自残方法、毒品制法、爆炸物与武器制法、现实暴力煽动
  六类，其中四类用**共现**命中（如 `少女` × `性行为`），避免误伤"命案/凶手/尸体/遗书"等叙事常用词；
  `高潮`、`呻吟` 已从拦截词表移除（`samples/回响-DEMO`、`黑魔法学徒的救赎` 的正常用法会被误拦）。
- 政治/观点类不做正则拦截（不可靠），改由 Prompt 规范 + L3 翻译层兜住。
- 实测：4 类违规描述经 `/api/generate-script`、`/api/realtime/start` 均返回 400 并给出正确分类；
  "18岁的少女在天台发现母亲的遗书"正常放行并完整生成。
